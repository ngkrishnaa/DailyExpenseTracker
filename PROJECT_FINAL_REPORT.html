Chapter 1: Project Overview & Problem Statement

1.1 Project Purpose

ExpenseFlow is a production-deployed, full-stack personal finance web application built to empower users with intentional spending habits, automated monthly budgeting, and deep spending analytics. The application provides an elegant, distraction-free environment where individuals record multi-category transactions, set financial boundaries, receive real-time threshold warnings, and export clean financial reports.

1.2 Problem Statement

Over 70% of students and working professionals encounter end-of-month financial distress due to untracked micro-spending across multiple cash and digital channels (UPI, cards, net banking). Traditional tracking alternatives suffer from severe limitations:

  • Spreadsheet Friction: Excel and Google Sheets lack automated input validation, have poor mobile usability, and offer zero automated budget overrun alerts.
  • Commercial App Privacy Invasions: Mainstream fintech apps (such as Cred, Walnut, or YNAB) aggressively demand access to personal SMS inboxes, bank logins, or credit bureau files to monetize user financial data.
  • Device Lock-in: Many mobile apps store data locally on a single device without cloud synchronization or charge expensive recurring subscriptions for basic CSV exports.

1.3 Proposed Solution & Key Objectives

ExpenseFlow solves these challenges by providing an institutional-grade, cloud-synchronized web platform with zero subscription costs and zero bank credential scraping. Key objectives include:

  • Universal Accessibility: Responsive web application accessible from any desktop, tablet, or smartphone browser.
  • Dual Authentication: Standard email/password login verified by OTP alongside 1-click Google OAuth 2.0 social authentication.
  • Budget Watchdog: Real-time budget progress calculation with 80% (Warning), 90% (Critical), and 100%+ (Exceeded) smart notifications.
  • Exact Financial Math: Strict fixed-point arithmetic using DECIMAL(12, 2) preventing floating-point penny drift.
  • Cloud Network Resilience: Zero-cost transactional email pipeline bypassing cloud host SMTP firewall blocks via Google Apps Script HTTPS Webhooks.

Chapter 6: Database Schema & Relational Integrity

The relational schema is implemented in MySQL 8.0 across 6 dedicated tables:

Relational Tables Summary
users (Accounts) • expenses (Transactions) • budgets (Monthly limits) • notifications (Alerts) • auth_otps (Hashed verification codes) • app_settings (Runtime configurations).

Data Integrity Highlights:

  • Exact Fixed-Point Math: Transaction amounts use DECIMAL(12, 2) rather than binary floating-point (FLOAT/DOUBLE), preventing cumulative penny rounding errors.
  • Referential Cascading: All child tables reference users(id) ON DELETE CASCADE, guaranteeing that purging a user automatically and atomically removes their associated expenses, budgets, and alerts.
  • B-Tree Composite Indexing: Queries leverage composite indexes such as idx_expenses_user_date (user_id, expense_date) and idx_expenses_user_category (user_id, category) to perform O(log N) searches instead of slow O(N) table scans.
  • Unique Relational Constraints: The budgets table enforces UNIQUE KEY unique_user_month_budget (user_id, month, year) at the database engine level, making duplicate budgets for the same month physically impossible.

Chapter 7: Authentication & Google OAuth 2.0

ExpenseFlow implements dual-authentication architecture:

1. Local Credential Authentication:

Passwords are never stored in plaintext. They are transformed using Werkzeug's implementation of PBKDF2-SHA256 with a unique 16-byte random salt. Password verification runs in constant time to prevent side-channel timing attacks.

2. Google OAuth 2.0 Social Authentication:

Implements the standard OAuth 2.0 Authorization Code Flow:

  1. User clicks "Sign in with Google" ➔ Flask generates a cryptographically random state token (via secrets.token_urlsafe(24)) and stores it in session.
  2. User is redirected to Google Identity Services with client ID and state.
  3. Google returns authorization code to /login/google/callback?code=...&state=....
  4. Flask validates the state parameter using hmac.compare_digest to completely neutralize Login CSRF attacks.
  5. Flask sends an internal server-to-server POST to https://oauth2.googleapis.com/token to exchange the authorization code for an access token.
  6. Flask queries https://www.googleapis.com/oauth2/v2/userinfo to obtain verified profile details.
  7. Automatic Account Linking: If the Google email matches an existing local user, the system links google_id to the existing account, preventing duplicate accounts and preserving existing expense history.

Chapter 8: OTP Verification Engine & Security

The One-Time Password (OTP) verification engine powers both user registration and password recovery:

Cryptographic Generation & Storage:

  • Generation: 6-digit uniform numerical code generated via Python's CSPRNG: secrets.randbelow(900000) + 100000.
  • Hashed Storage: The database never stores plaintext OTPs. Codes are hashed using PBKDF2-SHA256 before writing to auth_otps. If an attacker dumps the database, they obtain only irreversible hashes.
  • 10-Minute Expiration: Codes expire strictly 10 minutes after generation.
  • 5-Attempt Lockout: Failed attempts increment an attempt counter. If attempts >= 5, the record is immediately invalidated (is_used=TRUE), preventing brute-force attacks (guessing probability is 5 in 900,000 = 0.00055%).
  • Replay Prevention: Once verified or resent, prior codes are marked is_used=TRUE, preventing replay attacks.

Chapter 9: Production Email Architecture (₹0 HTTPS Solution)

The Cloud Deployment Dilemma:

When deploying to cloud platforms like Railway, standard SMTP connections to smtp.gmail.com:587 hang and fail because cloud security groups permanently block outbound TCP ports 25, 465, and 587 to prevent spam abuse. Furthermore, free API sandbox tiers (such as Resend) restrict email delivery exclusively to the developer's registered account, returning HTTP 403 when arbitrary end users register.

The Engineered Solution: Google Apps Script Webhook

To overcome both obstacles without purchasing custom domains or paid email APIs, we engineered an HTTPS Webhook using Google Apps Script:

Railway Production Server (app.py)
       |
       | HTTPS POST (Standard Port 443 — Never Blocked)
       | JSON Payload: {"to": recipient, "subject": sub, "text": txt, "html": html}
       v
Google Apps Script Webhook Endpoint (script.google.com)
       |
       | Executes inside Google's Datacenter via MailApp.sendEmail()
       v
User Inbox (Any Domain: Gmail, Outlook, Yahoo, Institutional)

Benefits: Bypasses cloud port blocks via Port 443; delivers up to 100 free emails per day to any recipient domain; authenticated by Google's native SPF/DKIM infrastructure; operates at ₹0 cost.

The analytics engine executes SQL grouping queries directly in MySQL:

  • Category Distribution: SELECT category, SUM(amount) FROM expenses GROUP BY category. Injected into Chart.js to render a responsive Doughnut chart.
  • Daily Spending Trend: SELECT expense_date, SUM(amount) FROM expenses GROUP BY expense_date ORDER BY expense_date ASC. Injected into Chart.js to render a smooth Line chart.

Chapter 13: Deployment Pipeline on Railway

The application is deployed on Railway PaaS with automated Continuous Deployment:

  1. Developer executes git push origin main to GitHub.
  2. Railway webhook detects commit and launches a container build.
  3. Container builds Python 3.11+ environment and executes pip install -r requirements.txt.
  4. Gunicorn starts via Procfile: web: gunicorn --workers 1 --threads 8 --bind 0.0.0.0:$PORT app:app.
  5. Railway injects encrypted environment variables (MYSQL_URL, FLASK_SECRET_KEY, GAS_WEBAPP_URL).
  6. Railway pings the container socket; upon receiving HTTP 200, it performs an atomic zero-downtime cutover.

Chapter 15: Technical Challenges & Engineering Lessons

  • Challenge 1 (Cloud Host SMTP Block): Railway blocks ports 25, 465, and 587. Resolved by routing transactional emails over standard HTTPS Port 443 via Google Apps Script.
  • Challenge 2 (Resend Sandbox 403): Free Resend sandbox rejected arbitrary test users. Resolved by leveraging Google Apps Script's universal delivery without domain requirements.
  • Challenge 3 (Google Drive Multi-Account Collision): Authorizing Apps Script in a browser with multiple active Google accounts yielded "Sorry, unable to open file". Resolved by deploying through an isolated Incognito session.
  • Challenge 4 (MySQL Idle Disconnects): Railway terminates idle TCP connections. Resolved by implementing active socket health pinging in ensure_db_connection().

Chapter 16: Top Viva Voce & Technical Interview Questions

Below are 15 critical questions and answers selected from the complete 55-question guide in PROJECT_VIVA_QA.md:

Q1: Why did you use DECIMAL(12, 2) instead of FLOAT for expense amounts?
SHORT ANSWER: FLOAT is an imprecise binary floating-point type that introduces rounding errors in financial balances. DECIMAL(12, 2) is an exact fixed-point type that guarantees penny-perfect accuracy.
In IEEE 754 binary floating-point representation, numbers like 0.10 cannot be stored precisely, resulting in values like 0.10000000000000000555. Adding thousands of transactions causes cumulative drift. DECIMAL(12, 2) stores numbers as exact binary-coded decimal digits, supporting up to 10 integer digits and 2 exact decimal places.
Q2: How does the application prevent SQL Injection?
SHORT ANSWER: We strictly use parameterized SQL queries (cursor.execute(sql, (param1, param2))) across every database call. User input is never concatenated into SQL query strings.
The MySQL database protocol transmits the query blueprint and parameters in separate network packets. The database engine never interprets the parameters as executable SQL syntax, making SQL injection attacks mathematically impossible.
Q3: Why did standard SMTP fail when deployed to Railway?
SHORT ANSWER: Cloud hosting providers like Railway permanently block outbound traffic on standard SMTP ports (25, 465, and 587) to prevent spammers from abusing their IP addresses.
While SMTP works locally because residential ISPs leave port 587 open, cloud platforms block raw TCP connections on mail ports. We resolved this by routing transactional emails over HTTPS port 443 to a Google Apps Script Webhook.
Q4: Why do you hash OTP verification codes in MySQL?
SHORT ANSWER: Hashing ensures that if an attacker dumps the database, they cannot read active OTPs or hijack user accounts during password reset.
Just like passwords, temporary authentication codes are sensitive credentials. We store only the irreversible PBKDF2-SHA256 hash in auth_otps and evaluate candidates using check_password_hash(). Even with read access to the database, an attacker cannot reverse the hash within the 10-minute validity window.
Q5: How does the system prevent Cross-Site Request Forgery (CSRF)?
SHORT ANSWER: We generate a 32-byte cryptographically random session token that must be submitted with every POST request and validated in constant time using hmac.compare_digest.
Every HTML form embeds a hidden CSRF token. When submitted, @app.before_request compares the form token against the user's signed session cookie using constant-time comparison. Because cross-origin sites cannot read the victim's session cookie due to SameSite policies, forged requests fail with HTTP 400.
Q6: What is the purpose of the OAuth 2.0 state parameter?
SHORT ANSWER: The state parameter acts as a one-time CSRF token that prevents an attacker from tricking a victim into linking the attacker's Google account to the victim's session.
Without state validation, an attacker could initiate an OAuth flow, capture their authorization code, and trick a victim into clicking the callback URL. The victim's account would be bound to the attacker's Google login. Comparing the returned state against session memory ensures the entity completing the flow initiated it.
Q7: How do you enforce data isolation between different users?
SHORT ANSWER: Every SQL query that reads, updates, or deletes expenses explicitly filters on WHERE user_id = session['user_id']. Users can never access another user's records.
We completely eliminate Insecure Direct Object References (IDOR). Even if an attacker authenticated as User 5 submits a POST request to /expenses/99/delete where expense 99 belongs to User 8, the query affects 0 rows because the WHERE clause checks both ID and user_id.
Q8: What is Werkzeug ProxyFix and why is it needed on Railway?
SHORT ANSWER: ProxyFix inspects reverse proxy headers like X-Forwarded-Proto, informing Flask that it is running behind an HTTPS reverse proxy on Railway.
Railway terminates public HTTPS and forwards internal requests over plain HTTP. Without ProxyFix, Flask generates insecure http:// URLs, breaks Google OAuth redirect URI matching, and refuses to set Secure cookie flags.
Q9: What happens if a user enters 5 incorrect OTP codes?
SHORT ANSWER: The system permanently invalidates the OTP record (is_used = TRUE), clears the reset session, and forces the user to request a brand new verification code.
This rate-limiting mechanism reduces the mathematical probability of guessing a 6-digit code to 5 in 900,000 (0.00055%), completely neutralizing automated brute-force attacks.
Q10: Why did you choose Gunicorn with 1 worker and 8 threads?
SHORT ANSWER: Threads provide concurrent request handling while sharing memory-resident OTP and registration verification structures within a single Python process.
Running multiple separate worker processes without an external cache like Redis would cause in-memory state (like pending_registrations) to be inaccessible across workers. 1 worker with 8 threads handles concurrent web traffic while preserving process memory.
Q11: What is ON DELETE CASCADE and why is it used?
SHORT ANSWER: It is a foreign key rule that automatically deletes all child records (expenses, budgets, notifications) when the parent user account is deleted.
Without ON DELETE CASCADE, deleting a user record would either trigger foreign key constraint errors or leave orphaned transaction records in the database with non-existent user_ids.
Q12: How does CSV export work without creating temporary disk files?
SHORT ANSWER: The application uses Python's io.StringIO in-memory text buffer to stream CSV data directly to the client HTTP response.
Writing temporary files to server disk risks disk space exhaustion, race conditions, and permission issues. io.StringIO formats CSV rows in RAM and returns them as a streaming attachment response.
Q13: How does the budget notification engine prevent duplicate alert spam?
SHORT ANSWER: Before creating an alert, the engine queries the notifications table to check if an alert of that specific type has already been emitted during the current month.
If a user is at 92% of their budget, recording another expense would otherwise trigger a redundant 90% warning on every page visit. Checking existing notification records ensures each threshold alert is emitted at most once per month.
Q14: What is the live URL and deployment environment of ExpenseFlow?
SHORT ANSWER: The live production application is hosted at https://dailyexpensetracker-production-bf76.up.railway.app on Railway PaaS paired with a cloud MySQL database.
The deployment is automatically triggered from the main branch on GitHub, utilizing Nixpacks containerization, Gunicorn WSGI, and automated TLS certificate termination.
